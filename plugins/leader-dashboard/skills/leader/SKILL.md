# 今日のリーダー

利用者は判断だけを受け持ち、Claude は段取り・下書き・後始末を受け持つ。

**ダッシュボード（HTML）を利用者とのやり取りの窓口にする。** 判断の材料・下書き・図はダッシュボードに置き、チャットの報告は短くする（長い報告をチャットで読むのは利用者の負担になる）。利用者への返事と動いたことは、チャットではなく `leader.json` に書く（`reply.py` を使う）。画面はそれを拾って利用者に知らせる。

**リーダーの会話には要約だけを置く。** 資料・下書き・やり取りの詳しいことは、プロジェクトごとの担当のエージェント（`project-lead`）が持ち、画面と引き継ぎのメモに置く。一日続けても会話が膨らまないようにするため。

道具はこのスキルの `scripts/` にある。

| 道具 | 使うのは | 役目 |
| --- | --- | --- |
| `server.py` | リーダー | ダッシュボードのサーバー。`items.json` と `items/*.json` を要求のたびに読み直し、答えを `decisions.jsonl` に1行ずつ足す |
| `wait_decision.sh` | リーダー | 答えが届くまで待つ。`cursor` を付けると、待つだけで中身は出さない |
| `route.py` | リーダー・担当 | 振り分けていない答えを、プロジェクトごとにまとめて短く出す。担当の名簿も書く |
| `item.py` | 担当 | `items/<project>.json` の項目・問い・下書き・担当の状態を書き換える |
| `reply.py` | リーダー・担当 | `leader.json` に返事・状態・動いたことを書く |
| `index.html` | — | 画面。4秒ごとに状態を取り直す |
| `leader_hook.py` | フック | 会話の始めと利用者の発言ごとに、作業フォルダーの様子を短く出す（「フック」の節） |

担当の定義はプラグインの `agents/project-lead.md`（エージェントの種類は `leader-dashboard:project-lead`）。

## コンテキストの決まり

- **リーダーが持つのは要約だけ。** プロジェクトごとの1行・判断待ちの数・担当の ID。詳しいことは画面と `handoff/` のメモにある
- **下書きの本文や長いファイルを自分で読まない。** 中身の確かめが要るなら担当に聞く。`decisions.jsonl` も直接読まず、`route.py` を通す
- **プロジェクトが2つ以上なら、プロジェクトごとに担当を1本出す。** タスクごとには出さない。同じ担当が一日そのプロジェクトを受け持つ
- **答えは `route.py` で振り分ける。** 担当のいるプロジェクトの答えは、出た行をそのまま SendMessage で回す。判断の中身に立ち入らない
- **担当とのやり取りは短く。** 指示は要点だけ、報告は5行以内。長い報告が来たら「5行で」と返し、本文はチャットに写さない
- **チャットは短く。** 詳しいことは画面に置く
- **会話が長くなったら、メモを最新にしてから圧縮する。** 担当にメモの更新を頼み、`handoff/_leader.md` を書いてから、利用者に `/compact` を勧める（「7. 引き継ぎのメモと再開」）
- **翌日や別のセッションでは、名簿（`roster.json`）の ID は使えない。** メモから担当を出し直す

## 流れ

1. タスクを洗い出し、プロジェクトに分ける
2. 作業フォルダーを作り、サーバーを起動する
3. プロジェクトごとに担当を出す
4. 利用者に URL を知らせ、答えを待つ
5. 答えを振り分け、また待つ
6. 担当の報告を受ける
7. 会話が長くなったら、メモを最新にして圧縮する
8. 終わったらサーバーを止める

## 1. タスクを洗い出し、プロジェクトに分ける

- 材料は利用者が指したもの（挙げたタスク、TODO の置き場、予定、受信箱など）。どこを見ればよいか分からなければ聞く。
- タスクをプロジェクト（画面のタブ）にまとめる。タブは5つほどまでにする。1つのタスクは1つの項目になる。
- 洗い出した一覧と、出す担当の本数をチャットに短く書き、そのまま進める。止めて確かめるのは、範囲がはっきりしないときだけ。

## 2. 作業フォルダーとサーバー

作業フォルダーはその日ごとに作る。**決まりの場所は `<カレントディレクトリ>/.leader/<今日の日付>`**（例: `.leader/2026-11-19`）。別の場所に置くときや、日付をまたいで続けるときは、環境変数 `LEADER_DASHBOARD_DIR` で指す（フックもこの順で探す）。**git に入れない**（下書きや判断に私的な情報が入る）。git のリポジトリの中なら、`.git/info/exclude` に `.leader/` の行を足す（追跡しているファイルを変えずに済む）。

サーバーは Bash の `run_in_background: true` で起動する。

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/server.py --dir .leader/2026-11-19 --port 8765 --root .
```

- 出力の1行目に URL が出る。ポートが使用中で起動できなければ、別のポート（8766 など）で起動し直す。
- `--root` は下書きの `src` を読む起点（既定はカレントディレクトリ）。その外のファイルは読まない。
- 作業フォルダーが無ければ作る。無いファイルは空として扱う。

作業フォルダーの中身:

| ファイル | 書くのは | 中身 |
| --- | --- | --- |
| `items.json` | リーダー | 題・見出し・予定・タブの並び。担当のいない項目もここに書いてよい |
| `items/<project>.json` | 担当（`item.py`） | プロジェクトごとの項目と担当の状態。サーバーが `items.json` と合わせて返す |
| `drafts/` | 担当 | 下書き |
| `handoff/<project>.md` | 担当 | 引き継ぎのメモ。再開するときはこれだけ読む |
| `handoff/_leader.md` | リーダー | リーダーの引き継ぎのメモ |
| `roster.json` | リーダー（`route.py --roster`） | 担当の名簿。プロジェクト → エージェントの ID・始めた時刻・最後の要約 |
| `leader.json` | `reply.py` | 返事・状態・動いたこと・見出し。手で書かない |
| `decisions.jsonl` | サーバー | 利用者の答え。1行に1件 |
| `cursor` | `route.py --ack` | 振り分け済みの `decisions.jsonl` の行数 |
| `server.json` | サーバー | 起動中の URL・pid・起動したセッション。止まると消える |

## 3. プロジェクトごとに担当を出す

Agent ツールで、プロジェクトごとに1本出す。`subagent_type` は `leader-dashboard:project-lead`。互いに関係しないので、1つのメッセージでまとめて出し、並行に走らせる。役目と決まり（書いてよい所、しないこと、メモのテンプレート、報告の形）は定義に書いてあるので、プロンプトには次だけを入れる。

- プロジェクトの id と名前（例: `blog`／ブログ）
- 作業フォルダーと道具の場所（`${CLAUDE_SKILL_DIR}/scripts` の展開後の絶対パス）
- 材料の場所と、その日のタスク（利用者の言葉のまま）
- 前の担当がいれば「`handoff/<id>.md` から続ける」

出したら、返ってきたエージェントの ID を名簿に書く。

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/route.py .leader/2026-11-19 --roster blog --agent <ID>
```

- 担当の種類が見つからないときは、`general-purpose` を出す（プラグインの外でスキルだけを使っているときなど）。最初に `${CLAUDE_SKILL_DIR}/../../agents/project-lead.md` を読み、その役目で動くよう頼む。
- プロジェクトが1つで、タスクも2〜3件なら、担当を立てずに、タスクごとにエージェントを出してよい。エージェントには、下書きを `drafts/<項目の id>.md` に書くよう頼む。返すのは、3行以内の要約・判断が要ること・確かめていないことだけ。項目にするのはリーダー（`item.py` か `items.json`）。外に出る操作はさせない。
- `items.json` には、題（`title`）・見出し（`headline`）・予定（`schedule`）・タブの並びを書く。タブの並びは `projects` に id を並べる（名前は担当が `items/<id>.json` に書く）。

## 4. 知らせて、待つ

チャットには短く書く: URL（その場で開けるように）、判断待ちの件数、急ぎの件。材料と下書きはダッシュボードにあると添える。初めて使う利用者には「左のサイドバーでプロジェクトを選び、一覧から1件ずつ答える。j/k で移動、x で完了」と一言添える。

答えは Bash の `run_in_background: true` で待つ。

```
bash ${CLAUDE_SKILL_DIR}/scripts/wait_decision.sh .leader/2026-11-19 cursor
```

- `cursor`（振り分け済みの行数）より後に答えがあれば終わる。振り分けていない答えが残っていれば、すぐに終わる。
- 届いても 20 秒は待つ（続けて押された答えをまとめるため）。出すのは件数だけで、中身は `route.py` で読む。終わると通知が来る。
- 待っている間も、ほかの作業（担当の報告を受けるなど）を続けてよい。

## 5. 答えを振り分ける

待ちが終わったら、振り分けていない答えを読み、そのまま振り分け済みにする。

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/route.py .leader/2026-11-19 --ack
```

出力の例:

```
答え 4 件（decisions.jsonl の 12〜15 行目）
[blog] ブログ → 担当 a1b2c3（09:30 から・最後: 本文と告知の下書きを出した）
  #12 blog-publish-ok「直してから（直す所をメモに）」 メモ: 3枚目の写真は差し替える…（全文は --full）
  #14 一言: ［ブログ / 記事を公開する］告知は明日の朝でいい
  #15 完了にした：次の記事の題材を決める（blog-next）
[（全体）] → リーダー
  #13 一言: 昼は 12:30 から見られる
振り分け済み: 15 行目まで（残り 0 件）
```

`完了にした：<題>` と `未完了に戻した：<題>` は、画面の完了ボタンの行。ほかの答えと同じく担当に回す。担当は、引き継ぎのメモを直し、後始末（元の TODO を閉じるなど）をする。

- **担当のいるプロジェクト**: その塊の行をそのまま、担当の ID に SendMessage で送る。添えるのは「全文は `route.py <dir> --project <id> --from <最初の行番号> --full`」の一言だけ。届かなければ（前のセッションの ID など）、`handoff/<id>.md` から続ける担当を出し直し、名簿を書き直してから送る。
- **担当なし**: 小さければリーダーが動く（下の「リーダーが自分で答えるとき」）。大きければ担当を出す。
- **（全体）**: 項目に紐づかない一言。リーダーが読んで動き、`reply.py --log` で返事を書く。
- 振り分けたら、すぐ次の待ちを始める。チャットには、何件をどこに回したかを1行で書く。
- 中身を見るだけで振り分け済みにしたくないときは、`--ack` を付けずに打つ。

### リーダーが自分で答えるとき

`decisions.jsonl` の1行は `{"ts", "item", "qid", "choice", "note"}`。

- `qid` が `message` の行は、ヘッダーの「Claude に一言」からのメモで、本文は `note` にある。プロジェクトを開いているときに送られたものは、本文の頭に `［プロジェクト / 項目の題］` が付き、`item` にその項目の id が入る。
- `qid` が `__done__` の行は、完了ボタンの操作（`{"ts", "qid": "__done__", "item", "done": true|false}`）。画面の状態は、項目ごとの最後の操作で決まる（`true` なら済み、`false` なら済みから判断待ちに戻る）。担当のいない項目なら、リーダーが後始末をする。`_leader.md` を直し、元の TODO がローカルのファイルにあれば完了の印を付ける（`false` なら外す）。共有の場所にある TODO は、利用者に頼む。

- `choice` と `note` を合わせて読む。`note` が `choice` より具体的なら `note` に従う。
- 答えに沿って動いたら、返事を書く。返事は1〜2文で、したことと次に要ることを書く。

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/reply.py .leader/2026-11-19 --qid home-subscription --text "解約の手順を下書きに足した。解約はそちらで"
python3 -I ${CLAUDE_SKILL_DIR}/scripts/reply.py .leader/2026-11-19 --status home-budget done --log "家計の確認を終えた"
python3 -I ${CLAUDE_SKILL_DIR}/scripts/reply.py .leader/2026-11-19 --headline "残りの判断待ちは2件です"
```

- 項目の状態: `items.json` の項目は `reply.py --status`、`items/<id>.json` の項目は `item.py status`（担当がいればそちらに任せる）。
- 判断の要ることが新しく出たら、問いか項目を足す。答えた後に追いの問いが要るときは、新しい `id` で足す（同じ `id` だと前の答えが付いて見える）。

## 6. 担当の報告を受ける

担当は5行以内で返す（新しく分かったこと・判断待ちの数・リーダーに頼むこと・メモを直したこと）。

- 名簿の要約を1行で直す: `route.py <dir> --roster <id> --summary "<1行>"`
- 「リーダーに頼むこと」だけを扱う。外に出る操作は、利用者がその項目に答えたことを確かめてから（「守ること」）。ほかのプロジェクトに関わることは、その担当に回す
- 報告の本文はチャットに写さない。利用者に知らせたいことがあれば `reply.py --log` で1行

## 7. 引き継ぎのメモと再開

担当は `handoff/<id>.md` を保つ（テンプレートは担当の定義にある。現在地・判断待ち・触ったファイル・次の一手）。リーダーは `handoff/_leader.md` を保つ。

```markdown
# リーダーの引き継ぎ（2026-11-19）

更新: 14:05

## 今日の方針
- （利用者が言ったこと・任された範囲。3行まで）

## 担当
- blog: 担当あり。現在地は handoff/blog.md
- home: リーダーが直接見る（項目は items.json）

## 残っていること
- （急ぎ、利用者に頼まれて手を付けていないこと）

## サーバー
- server.py --dir <作業フォルダー> --port 8765 --root .
```

- **会話が長くなったら**: 各担当に「メモを最新にして」と SendMessage で頼み、`_leader.md` を直し、利用者に `/compact` を勧める。自動の圧縮に備え、区切りごとに `_leader.md` の「残っていること」を直しておく。
- **圧縮の後**: フックが作業フォルダーの様子を出す。`_leader.md` だけを読んで続ける。同じセッションの担当には、そのまま SendMessage で頼める。
- **翌日・別のセッション**: 名簿の ID は使えない。今日の作業フォルダーを作り、前の日の `handoff/` を写してから、担当を「`handoff/<id>.md` から続ける」で出し直し、名簿を書き直す。

## フック

プラグインにフックが入っている。作業フォルダーが見つからなければ何も出さない。

- **会話の始め**（起動・再開・`/clear`・圧縮の後）: ダッシュボードの URL と動いているか、プロジェクトごとの判断待ちの数、振り分けていない答えの数、引き継ぎのメモの場所を数行で出す。
- **利用者の発言ごと**: 振り分けていない答えがあれば「ダッシュボードに未処理の答えが N 件（route.py … で読める）」を1行だけ足す。
- 作業フォルダーを探す順:
  1. 環境変数 `LEADER_DASHBOARD_DIR`
  2. `<カレントディレクトリ>/.leader/<今日の日付>`
  3. `<プロジェクトのルート>/.leader/<今日の日付>`
- サーバーが動いていて、`server.json` の起動したセッションが今のセッションと違うときは、別のセッションがリーダーをしているとみなす。そのときは発言ごとの1行を出さない。同じフォルダーで並行するセッションが、答えを取り合わないようにするため。

## 8. 終わり

判断待ちが無くなり、利用者が区切りと言ったら、担当にメモの最後の更新を頼み、`--log` で今日の締めを1行書き、起動した裏のシェルを止めてサーバーを終える。待ちのシェルが残っていれば、それも止める。作業フォルダーは残す（その日の記録）。消すかは利用者が決める。

## 項目の書き方

担当は `item.py` で書く（使い方は `item.py --help`）。`items/<project>.json` の形は次のとおり。`items.json` の `items` にも同じ形の項目を書ける（そのときは各項目に `project` を書く）。

```json
{
  "project": {"id": "blog", "label": "ブログ",
              "lead": {"status": "waiting", "summary": "本文と告知の下書きを出した", "updated": "11/19 09:40"}},
  "items": [
    {
      "id": "blog-publish",
      "group": "今週の記事",
      "title": "記事を公開する",
      "status": "decide",
      "urgent": true,
      "summary": ["本文は約 1,200 字", "**公開のボタンを押すのは利用者**"],
      "details": ["経緯や根拠は「くわしく」に畳んで出る"],
      "links": [{"label": "管理画面", "url": "https://example.com/admin"}],
      "drafts": [
        {"label": "本文", "where": "編集画面に貼る", "link": "https://example.com/admin/new",
         "src": {"file": ".leader/2026-11-19/drafts/blog-publish.md", "heading": "## 本文", "whole": true}},
        {"label": "メモ", "text": "短い文面はここに直接書いてもよい"}
      ],
      "questions": [
        {"id": "blog-publish-ok", "text": "この本文で公開する？",
         "options": ["公開してよい", "直してから（直す所をメモに）", "保留"]}
      ],
      "svg": "<svg viewBox='0 0 600 120' width='100%'>...</svg>"
    }
  ]
}
```

| 欄 | 決まり |
| --- | --- |
| `project.lead` | 担当の状態。`status` は `working`（動いている）・`waiting`（利用者の答え待ち）・`idle`（手が空いた）。`summary` は1行。`item.py lead` で書く |
| `id` | 項目ごとに重ならない英数字 |
| `group` | 左の一覧の小見出し（任意） |
| `status` | `decide`（判断待ち）・`running`（進行中）・`done`（済み）。`leader.json` の状態が優先する（`item.py status` はそれを消して書く） |
| `urgent` | 今日のうちに答えが要るとき `true` |
| `summary` | 3行まで。結論、判断に要る数字、誰が何をするか。`**太字**` と `` `コード` `` が使える |
| `details` | 経緯・根拠・確かめていないこと。「くわしく」に畳まれる |
| `links` | 開いて確かめる先 |
| `drafts` | 下書き。`text` に直接書くか、`src` でファイルを指す。`link` は「開く」のリンク、`where` は貼る場所 |
| `questions` | 問い。`id` は**全項目を通して**重ならないようにする（`message` は使えない）。`options` はボタンになる |
| `svg` / `svg_file` | 図。`svg` は SVG の文字列をそのまま描く。`svg_file` は作業フォルダーからの相対パス |

`items.json` の一番外には、ほかに次を書く。

- `title`・`headline`: 画面の題と、全体のタブの見出し
- `schedule`: その日の予定。`[{"time": "10:00", "end": "11:00", "title": "打ち合わせ"}]`
- `projects`: タブの並び。`[{"id", "label"}]`

### 問いの書き方

- 選択肢には推奨を入れ、推奨を先頭に置く。ボタンになるので短く書く。
- 直してほしいときの選択肢（「直してから（直す所をメモに）」）と「保留」を必要に応じて入れる。利用者はどの問いにもメモを付けられる。
- 1つの問いでは1つのことを聞く。

### 下書きの `src`

毎回ファイルから読むので、エージェントや利用者がファイルを直すと画面にも出る。長い下書きは `text` より `src` で指す。

- `file`: `--root` からの相対パス。`--root` の外は読まない
- `heading`: 見出しの行の前方一致（`## 告知` は `## 告知の文` にも合う）。節は同じか浅い見出しの手前で終わる。コードブロックの中の `#` は見出しとみなさない。省くとファイル全体
- `nth`: 同じ見出しが何度も出るときの何番目か（既定は 1）
- 既定では、節の中の引用（`>`）の行だけを抜く。引用が無ければ最初のコードブロックの中身、それも無ければ節の全体
- `whole: true`: 節の全体をそのまま出す
- `between_rules: true`: 節の中の最初の2本の `---` に挟まれた所だけを出す

### 図

日程、分かれ道、案の比較のように、図で見ると判断が速くなるときに描く。

- `viewBox` を付け、`width='100%'` にする。幅は 900〜960 ほどで描く
- 属性を単引用符で書くと、JSON の中で引用符を逃がさずに済む
- `<script>`・`on...` の属性・`javascript:` のリンクは落とされる
- 大きい図は作業フォルダーに `.svg` を置き、`svg_file` で指す
- 画面は macOS の標準アプリの見た目（システムの色・ゴシック体・ライトとダークは Mac の設定に従う）。図も細い線とゴシックの字で描き、アクセントの色（Mac のアクセントカラー）は判断が要る1か所だけに使う。ルートの `<svg>` に `class='themed'` を付け、要素に次の class を付けると、画面の色とダークモードに合う
  - 塗り: `f-you`（アクセント。判断が要る所の字）・`f-ink`（本文の字）・`f-sub`・`f-muted`（弱い字）・`f-line`（区切りの色）・`f-surface`（地）・`f-on`（アクセントの上の字）
  - 線: `s-you`（アクセント）・`s-ink`（図の線）・`s-muted`・`s-line`（区切り）
  - 前の版の `f-claude`・`f-done`・`f-urgent` などの class も使えるが、墨か灰色になる
  - class の無い `<text>` は本文の色になる。`themed` を付けない図は、ダークモードでは明るい紙の上に出る。例は `examples/demo/items.json` の `trip-inn`

JSON が壊れている、`src` が読めない、`id` が重なっている、のどれかがあれば出力に出る（エラーなら終了コード 1）。読んだファイルの一覧も出る。画面の上にも同じ注意が出る。

## 画面が利用者に見せるもの

返事の書き方を決めるために知っておくこと。

- **サイドバー**: 左に「全体」とプロジェクトの一覧と今日の予定（`schedule`）。数字は判断待ちの件数。`←` `→` か `⌘1`〜（`1`〜でも）で移る
- **一覧**: 真ん中。Mail の形で、題・要約の1行目・状態を出す。判断待ちが先。`done` の項目は下の「済み N 件」に畳まれる。済みの項目では選択肢と入力欄が消える
- **1件**: 右。右上に「完了にする」（済みなら「未完了に戻す」）、要約、くわしく、図、問い（ラジオボタンとメモと「答える」）、下書き（開く・コピー）、リンク
- **担当**: `project.lead` があれば、担当の状態・1行・時刻が出る（プロジェクトの一覧の上と、全体の右）
- **完了のボタン**: 利用者は項目ごとに「完了」「未完了に戻す」を押せる。押すと `decisions.jsonl` に `__done__` の行が入り、画面の状態は最後の操作で決まる
- **更新の印**: 項目の `status`・`title`・`summary`・問いの文と返事・下書きのどれかが変わると、その項目とサイドバーに未読の点（アクセントの色）が付く。利用者が開くと見出しと返事に一度だけ淡い地が付き、既読になる。利用者自身の答えでは印は付かない
- **ツールバー**: 上。`leader.json` の `log` の最後の1行をいつも出す。新しい行が来ると右下の知らせ（5秒）で知らせ、サイドバーの「全体」に未読の点が付く
- **一言の欄**: ツールバーにあり、どこからでも送れる
- **全体**: 一覧はプロジェクトごとの項目（済みは畳む）。右に判断待ちの数、見出し（`headline`）、プロジェクトごとの判断待ちと済み（と担当）、「Claude の動き」（新しい順）、「送ったメモ」

このため、利用者に知らせたいことは `--log` で1行書く。項目の中身が変わったら `item.py` か `items.json` で項目を直す（印が付く）。

## 守ること

- **外に出る操作は、その項目への利用者の答えが届いてから。** 送信・投稿・予約・購入・削除・共有の設定の変更がこれに当たる。答えが「保留」や曖昧なら動かず、返事で聞き直す。担当やエージェントにはさせない（担当は「リーダーに頼むこと」に書いて返す）。
- **サーバーは 127.0.0.1 だけで受ける。** 待ち受けの先を変えない。トンネルや画面共有の道具で外に出さない。
- **作業フォルダーは git に入れない。** パスワードやトークンは、項目・下書き・メモのどれにも書かない。
- 項目を利用者の知らないうちに消さない。片付いたものは `done` にする。
- チャットに長い報告を書かない。材料はダッシュボードに置く。
