# 今日のリーダー

利用者は判断だけを受け持ち、Claude は段取り・下書き・後始末を受け持つ。

**ダッシュボード（HTML）を利用者とのやり取りの窓口にする。** 判断の材料・下書き・図はダッシュボードに置き、チャットの報告は短くする（長い報告をチャットで読むのは利用者の負担になる）。利用者への返事と動いたことは、チャットではなく `leader.json` に書く（`reply.py` を使う）。画面はそれを拾って利用者に知らせる。

道具はこのスキルの `scripts/` にある。

| 道具 | 役目 |
| --- | --- |
| `server.py` | ダッシュボードのサーバー。`items.json` を要求のたびに読み直し、答えを `decisions.jsonl` に1行ずつ足す |
| `index.html` | 画面。4秒ごとに状態を取り直す。Claude の変化には「更新」の印を付け、新しい「動いたこと」はヘッダーの帯とトーストで知らせる |
| `wait_decision.sh` | 答えが届くまで待ち、新しい行を出して終わる |
| `reply.py` | `leader.json` に返事・状態・動いたことを書く |

## 流れ

1. タスクを洗い出す
2. タスクごとにエージェントを出す
3. 作業フォルダーを作り、サーバーを起動する
4. 戻った結果を `items.json` の項目にする
5. 利用者に URL を知らせ、答えを待つ
6. 答えが来たら動き、返事を書き、また待つ
7. 終わったらサーバーを止める

## 1. タスクを洗い出す

- 材料は利用者が指したもの（挙げたタスク、TODO の置き場、予定、受信箱など）。どこを見ればよいか分からなければ聞く。
- 1つのタスクを1つの項目にする。項目はプロジェクト（画面のタブ）にまとめる。タブは5つほどまでにする。
- 洗い出した一覧と、出すエージェントの本数をチャットに短く書き、そのまま進める。止めて確かめるのは、範囲がはっきりしないときだけ。

## 2. タスクごとにエージェントを出す

Agent ツールで、タスクごとに1本出す。互いに関係しないものは1つのメッセージでまとめて出し、並行に走らせる。エージェントへの指示には次を入れる。

- 目的と、材料の場所
- 下書きの書き先: `<作業フォルダー>/drafts/<項目の id>.md`。貼って使う文面は見出し（`## ...`）の下に、引用（`>`）かコードブロックで書く。ダッシュボードはそこだけを抜き出し、コピーできる形で出す
- **しないこと**: 送信・投稿・予約・購入・削除・共有の設定の変更など、外に出る操作と取り消せない操作。下書きまでで止める
- 返すもの: 3行以内の要約、判断が要ること（問い・選択肢・推奨とその理由）、確かめていないこと

エージェントが戻るたびに項目を書き足す。全部がそろうのを待たない。走っている間の項目は `status: "running"` にしておく。

## 3. 作業フォルダーとサーバー

作業フォルダーはその日ごとに作る（例: `.leader/2026-11-19`）。**git に入れない**（下書きや判断に私的な情報が入る）。git のリポジトリの中なら、`.git/info/exclude` に `.leader/` の行を足す（追跡しているファイルを変えずに済む）。

サーバーは Bash の `run_in_background: true` で起動する。

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/server.py --dir .leader/2026-11-19 --port 8765 --root .
```

- 出力の1行目に URL が出る。ポートが使用中で起動できなければ、別のポート（8766 など）で起動し直す。
- `--root` は下書きの `src` を読む起点（既定はカレントディレクトリ）。その外のファイルは読まない。
- 作業フォルダーが無ければ作る。無いファイルは空として扱う。

作業フォルダーの中身:

| ファイル | 書くのは | 中身 |
| --- | --- | --- |
| `items.json` | Claude | 項目の定義。丸ごと書き直してよい。サーバーは要求のたびに読み直す |
| `leader.json` | `reply.py` | 返事・状態・動いたこと・見出し。手で書かない |
| `decisions.jsonl` | サーバー | 利用者の答え。Claude は読むだけ |
| `drafts/` | エージェント | 下書き |

## 4. items.json の書き方

```json
{
  "title": "今日のリーダー",
  "headline": "4本のエージェントが戻りました。判断待ちはタブの数字のとおりです",
  "schedule": [{"time": "10:00", "end": "11:00", "title": "打ち合わせ"}],
  "projects": [{"id": "blog", "label": "ブログ"}],
  "items": [
    {
      "id": "blog-publish",
      "project": "blog",
      "group": "今週の記事",
      "title": "記事を公開する",
      "status": "decide",
      "urgent": true,
      "summary": ["本文は約 1,200 字", "**公開のボタンを押すのは利用者**"],
      "details": ["経緯や根拠は「くわしく」に畳んで出る"],
      "links": [{"label": "管理画面", "url": "https://example.com/admin"}],
      "drafts": [
        {"label": "本文", "where": "編集画面に貼る", "link": "https://example.com/admin/new",
         "src": {"file": ".leader/2026-11-19/drafts/blog-publish.md", "heading": "## 本文", "whole": true}},
        {"label": "メモ", "text": "短い文面はここに直接書いてもよい"}
      ],
      "questions": [
        {"id": "blog-publish-ok", "text": "この本文で公開する？",
         "options": ["公開してよい", "直してから（直す所をメモに）", "保留"]}
      ],
      "svg": "<svg viewBox='0 0 600 120' width='100%'>...</svg>"
    }
  ]
}
```

| 欄 | 決まり |
| --- | --- |
| `id` | 項目ごとに重ならない英数字 |
| `project` | `projects` の `id`。`projects` に無い値はそのままタブになる |
| `group` | 左の一覧の小見出し（任意） |
| `status` | `decide`（判断待ち）・`running`（進行中）・`done`（済み）。`leader.json` の状態が優先する |
| `urgent` | 今日のうちに答えが要るとき `true` |
| `summary` | 3行まで。結論、判断に要る数字、誰が何をするか。`**太字**` と `` `コード` `` が使える |
| `details` | 経緯・根拠・確かめていないこと。「くわしく」に畳まれる |
| `links` | 開いて確かめる先 |
| `drafts` | 下書き。`text` に直接書くか、`src` でファイルを指す。`link` は「開く」のリンク、`where` は貼る場所 |
| `questions` | 問い。`id` は**全項目を通して**重ならないようにする（`message` は使えない）。`options` はボタンになる |
| `svg` / `svg_file` | 図。`svg` は SVG の文字列をそのまま描く。`svg_file` は作業フォルダーからの相対パス |

### 問いの書き方

- 選択肢には推奨を入れ、推奨を先頭に置く。ボタンになるので短く書く。
- 直してほしいときの選択肢（「直してから（直す所をメモに）」）と「保留」を必要に応じて入れる。利用者はどの問いにもメモを付けられる。
- 1つの問いでは1つのことを聞く。答えた後に追いの問いが要るときは、新しい `id` で足す（同じ `id` だと前の答えが付いて見える）。

### 下書きの `src`

毎回ファイルから読むので、エージェントや利用者がファイルを直すと画面にも出る。長い下書きは `text` より `src` で指す。

- `file`: `--root` からの相対パス。`--root` の外は読まない
- `heading`: 見出しの行の前方一致（`## 告知` は `## 告知の文` にも合う）。節は同じか浅い見出しの手前で終わる。コードブロックの中の `#` は見出しとみなさない。省くとファイル全体
- `nth`: 同じ見出しが何度も出るときの何番目か（既定は 1）
- 既定では、節の中の引用（`>`）の行だけを抜く。引用が無ければ最初のコードブロックの中身、それも無ければ節の全体
- `whole: true`: 節の全体をそのまま出す
- `between_rules: true`: 節の中の最初の2本の `---` に挟まれた所だけを出す

### 図

日程、分かれ道、案の比較のように、図で見ると判断が速くなるときに描く。

- `viewBox` を付け、`width='100%'` にする。幅は 900〜960 ほどで描く
- 属性を単引用符で書くと、JSON の中で引用符を逃がさずに済む
- `<script>`・`on...` の属性・`javascript:` のリンクは落とされる
- 大きい図は作業フォルダーに `.svg` を置き、`svg_file` で指す

### 書いたら点検する

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/server.py --dir .leader/2026-11-19 --root . --check
```

JSON が壊れている、`src` が読めない、`id` が重なっている、のどれかがあれば出力に出る（エラーなら終了コード 1）。画面の上にも同じ注意が出る。

## 画面が利用者に見せるもの

返事の書き方を決めるために知っておくこと。

- **タブ**: 全体のタブと、プロジェクトごとのタブ。タブの数字は判断待ちの件数
- **一覧**: タブの中の左。`done` の項目は下の「済み（N）」に畳まれる。済みの項目では選択肢と入力欄が消える
- **更新の印**: 項目の `status`・`title`・`summary`・問いの文と返事・下書きのどれかを Claude が変えると、その項目に「更新」の印が付き、タブに「更新 N」が出る。利用者が開くと見出しと返事が黄色く光り、既読になる。利用者自身の答えでは印は付かない
- **ヘッダーの帯**: `leader.json` の `log` の最後の1行をいつも出す。新しい行が来るとトースト（5秒）で知らせ、全体のタブに「新着 N」が出る
- **一言の欄**: ヘッダーにあり、どのタブからでも送れる
- **全体のタブ**: 項目の図（済みは既定で隠す）、「Claude からの返事・動いたこと」（新しい順）、「送ったメモ」

このため、利用者に知らせたいことは `--log` で1行書く。項目の中身が変わったら `items.json` か `reply.py` で項目を直す（印が付く）。

## 5. 知らせて、待つ

チャットには短く書く: URL（その場で開けるように）、判断待ちの件数、急ぎの件。材料と下書きはダッシュボードにあると添える。初めて使う利用者には「タブを選び、左の一覧から1件ずつ答える。j/k で移動」と一言添える。

答えは Bash の `run_in_background: true` で待つ。

```
bash ${CLAUDE_SKILL_DIR}/scripts/wait_decision.sh .leader/2026-11-19 0
```

- 2つ目の引数は基準の行数。初めは今の `decisions.jsonl` の行数（新しい作業フォルダーなら 0）。
- 行が増えると、続けて押された答えもまとめるため 20 秒待ってから、新しい行と最後に `next_base=N` を出して終わる。終わると通知が来る。
- 次に待つときは、その `N` を基準に渡す。待っていない間に届いた答えも取りこぼさない。
- 待っている間も、ほかの作業（戻ったエージェントの結果を項目にするなど）を続けてよい。

## 6. 答えを受けて動く

`decisions.jsonl` の1行の形:

```json
{"ts": "2026-11-19 14:05:12", "item": "blog-publish", "qid": "blog-publish-ok", "choice": "公開してよい", "note": ""}
```

`qid` が `message` の行は、ヘッダーの「Claude に一言」からのメモ。本文は `note` にある。項目のタブから送られたものは、本文の頭に `［タブ / 項目の題］` が付き、`item` にその項目の id が入る。

- `choice` と `note` を合わせて読む。`note` が `choice` より具体的なら `note` に従う。
- 答えに沿って動いたら、返事を書く。返事は1〜2文で、したことと次に要ることを書く。

```
python3 -I ${CLAUDE_SKILL_DIR}/scripts/reply.py .leader/2026-11-19 --qid blog-publish-ok --text "公開用の最終版にした。公開のボタンはそちらで"
python3 -I ${CLAUDE_SKILL_DIR}/scripts/reply.py .leader/2026-11-19 --status blog-publish done --log "記事の公開を確かめた"
python3 -I ${CLAUDE_SKILL_DIR}/scripts/reply.py .leader/2026-11-19 --headline "残りの判断待ちは2件です"
```

- 項目が片付いたら `--status <項目の id> done`。判断の要ることが新しく出たら、`items.json` に問いか項目を足す。
- 一言への返事は `--log` で書く。
- 返事を書いたら、すぐ `next_base` を基準に次の待ちを始める。
- チャットには、何件に答えて何をしたかを1〜2行で書く。中身は画面で読める。

## 7. 終わり

判断待ちが無くなり、利用者が区切りと言ったら、`--log` で今日の締めを1行書き、起動した裏のシェルを止めてサーバーを終える。待ちのシェルが残っていれば、それも止める。作業フォルダーは残す（その日の記録）。消すかは利用者が決める。

## 守ること

- **外に出る操作は、その項目への利用者の答えが届いてから。** 送信・投稿・予約・購入・削除・共有の設定の変更がこれに当たる。答えが「保留」や曖昧なら動かず、返事で聞き直す。エージェントにもさせない。
- **サーバーは 127.0.0.1 だけで受ける。** 待ち受けの先を変えない。トンネルや画面共有の道具で外に出さない。
- **作業フォルダーは git に入れない。** パスワードやトークンは、`items.json` と下書きのどちらにも書かない。
- 項目を利用者の知らないうちに消さない。片付いたものは `done` にする。
- チャットに長い報告を書かない。材料はダッシュボードに置く。
